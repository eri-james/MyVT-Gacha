The codebase consists of approximately 6,860 lines of vanilla HTML, CSS, and JavaScript spread across 7 files, with no build tools, frameworks, or external dependencies beyond a single JSON data file. ### 2.2 Architecture Pattern

All JavaScript modules use the **Revealing Module Pattern** (IIFE with a public API object). This provides clean namespacing and encapsulation without requiring a build step. The dependency graph is linear and unidirectional:

```
DataLoader → Game → Gacha → Characters → UI
```

### 2.3 Key Technical Decisions

- **localStorage persistence** with version migration (currently v2), multi-slot save system (Sprint 6)
- **1-second interval tick loop** for real-time resource generation
- **12-hour offline earnings cap** with per-minute income calculation
- **3-rate gacha system** (Normal 82%, SR 15%, SSR 3%) with 50-pull pity threshold
- **Character ascension** from Normal → SR → SSR using star fragments
- **Export/import save codes** via base64 + TextEncoder/TextDecoder
- **Odekake expedition system** (Sprint 7) — timed character missions unlocked at Studio Lv 10

## 3. Critical Bugs

### CR-01: Double Division in Tick Loop — FIXED ✅

**Impact:** Real-time income was 60x slower than displayed offline rates.

In `game.js`, the `startTickLoop()` function calculated per-second income by calling `calculatePerMinuteIncome(1/60)`, which correctly returns earnings for one second. However, the function then divided each resource value by 60 again before adding it to the state. This resulted in the player earning only 1/3600th of the intended per-minute rate per second.

The offline earnings path (`claimOfflineEarnings`) called `calculatePerMinuteIncome` directly and added the result without the extra division, creating a **60x discrepancy** between real-time and offline income rates.

**Fix applied:** Removed the extra `/60` division. `earnings.stars` is now added directly.

---

### CR-02: Infinite Loop in addStudioExp() — FIXED ✅

**Impact:** Game froze when studio gained enough EXP for multiple level-ups.

The `nextLevel` variable was computed **before** the while loop and never reassigned inside it. After the first iteration leveled up the studio, the loop condition still checked against the old threshold, creating an infinite loop. This would trigger whenever a player claimed offline earnings granting enough studio EXP to level up more than once.

**Fix applied:** Rewritten with `while(true)` and `next` computed inside the loop:

```js
function addStudioExp(amount) {
  state.studio.exp += amount;
  while (true) {
    const next = STUDIO_LEVELS.find(l => l.level === state.studio.level + 1);
    if (!next || state.studio.exp < next.exp) break;
    state.studio.level = next.level;
    if (next.level >= STUDIO_LEVELS.length) break;
  }
}
```

### CR-03: SSR Streak Tracking Error in Multi-Pull — FIXED ✅

**Impact:** SSR streak statistic was artificially inflated.

The `pullMulti()` function includes a guarantee that the 10th pull will be at least SR. When this guarantee activated, the code unconditionally incremented `state.stats.ssrStreak` regardless of whether the forced pull was SSR or SR (85% chance). If SR, the streak counter incremented without an actual SSR pull.

**Fix applied:** SSR streak now only increments on actual SSR in the guarantee block; SR resets it:

```js
if (i === 9 && !hasSR) {
  variant = Math.random() < 0.85 ? 'sr' : 'ssr';
  if (variant === 'ssr') {
    state.pity.count = 0;
    state.stats.ssrStreak++;
    if (state.stats.ssrStreak > state.stats.bestSsrStreak)
      state.stats.bestSsrStreak = state.stats.ssrStreak;
  } else {
    state.stats.ssrStreak = 0;
  }
}
```

## 4. High-Priority Issues

### HP-01: Featured Banner Characters Regenerate on Every Display — FIXED ✅

`updateBannerInfo()` called `Gacha.generateFeatured()` every time it ran (on every tab switch and after every pull), creating new random featured characters each time. The actual pull logic used a different array set during init. The banner description showed different featured characters than what the player was actually pulling.

**Fix applied:** Featured character names cached in `_cachedFeaturedNames` during `setupFeaturedBanner()` and reused for display.

---

### HP-02: pullSingle() Does Not Trigger State Change Callback — FIXED ✅

`pullSingle()` had an empty `if (Game.onStateChange) {}` no-op block, causing up to 1-second UI delay after a single pull.

**Fix applied:** Replaced with direct `Game.save()` call which triggers `_onStateChange` internally.

---

### HP-03: Potential XSS via onclick Attribute Injection — FIXED ✅

`showCharacterDetail()` built HTML strings with inline `onclick="UI.levelUpChar('${slug}')"` handlers. If a character slug contained single quotes or HTML special characters, this would create a DOM-based XSS vulnerability.

**Fix applied:** All inline `onclick` handlers replaced with `data-action` attributes and `addEventListener` delegation pattern:

```js
detail.querySelectorAll('[data-action]').forEach(btn => {
  btn.addEventListener('click', () => {
    const action = btn.dataset.action;
    const s = btn.dataset.slug;
    if (action === 'levelup') levelUpChar(s);
    else if (action === 'ascend') ascendChar(s);
    else if (action === 'convert-shards') convertShards(s, btn.dataset.resource);
  });
});
```

---

### HP-04: DataLoader Race Condition — FIXED ✅

`DataLoader.load()` had no guard against concurrent calls. Multiple modules calling `DataLoader.get()` before fetch completed would receive an empty array. Also no HTTP status code checking on the fetch response.

**Fix applied:** Added `_loading` guard for concurrent calls + `resp.ok` status check with error throwing.

---

### HP-05: Deprecated escape/unescape in Save Import — FIXED ✅

`importSaveCode()` used deprecated `escape()`/`unescape()` functions for UTF-8 base64 encoding.

**Fix applied:** Replaced with `TextEncoder`/`TextDecoder`:

```js
function exportSaveCode() {
  const json = JSON.stringify(state);
  const bytes = new TextEncoder().encode(json);
  const b64 = btoa(String.fromCharCode(...bytes));
  return b64;
}

function importSaveCode(code) {
  const bytes = Uint8Array.from(atob(code.trim()), c => c.charCodeAt(0));
  const json = new TextDecoder().decode(bytes);
  // ...
}
```

Offline and real-time income paths produced wildly different results due to CR-01's double division.

**Fix applied:** Both paths now use the same `calculatePerMinuteIncome()` function, which internally calls `getStationIncome()`. The discrepancy is eliminated.

## 5. Medium-Priority Issues

### MP-01: Duplicated Income Calculation Logic — FIXED ✅

The per-station income formula was duplicated in `calculatePerMinuteIncome()` and `getStationIncome()`.

**Fix applied:** `calculatePerMinuteIncome()` now calls `getStationIncome()` internally, eliminating duplication.

---

### MP-02: No Input Validation on Save Import — OPEN

`importSaveCode()` only validates that decoded JSON has `version` and `playerId` fields. No validation of nested objects (currencies, characters, studio). A malformed save code could set negative currencies or corrupt character data.

**Recommendation:** Add structural validation (positive currency values, valid character slugs, station levels within bounds).

---

### MP-03: Full DOM Re-render on Every Tick — OPEN

`updateUI()` is called every second by the tick loop, updating ~15-20 DOM elements regardless of which tab is active. Includes conditional re-renders of studio tab, collection progress, and profile tab.

**Recommendation:** Only update resource counters on each tick. Defer full UI refresh to user-initiated events (tab switches, pulls, actions).

---

### MP-04: Magic Numbers Throughout Codebase — OPEN

Constants like pull costs (100, 1000), pity threshold (50), collection page size (40), log caps (50), auto-save interval (30000ms), and offline cap (12 hours) are partially defined as named constants and partially used inline.

**Recommendation:** Centralize all game balance constants into a single `CONFIG` object or module.

---

### MP-05: No Debounce on Auto-Save During Rapid Actions — FIXED ✅

Multiple synchronous localStorage writes within milliseconds during rapid actions (repeated level-ups, station assignments).

**Fix applied:** `saveDebounced()` added with 500ms debounce timer.

---

### MP-06: Characters Module Does Not Trigger UI Refresh — OPEN

`levelUp()` and `ascend()` in `characters.js` call `Game.save()` but do not call the state change callback. UI only refreshes because calling code in ui.js explicitly calls `updateUI()` — an implicit contract that could break with new callers.

**Recommendation:** Make the pattern consistent: always trigger callback from within action functions, or document that callers must handle UI refresh.

---

### NEW-01: isCharacterBusy() Does Not Check Station Assignments — OPEN

**Found during Sprint 7 re-check.** `isCharacterBusy()` only checks if a character is on an active expedition. It does not check if the character is currently assigned to a station. This allows a character to simultaneously earn station income AND expedition rewards — a double-dip exploit. The code comment says "on another expedition or assigned to station" but the implementation only checks expeditions.

**Location:** `game.js`, `isCharacterBusy()` (Sprint 7)

**Fix:**

```js
function isCharacterBusy(slug) {
  if (state.odekake.expeditions.some(e => e.characterSlug === slug)) return true;
  return !!getCharacterStation(slug);
}
```

## 6. Low-Priority Suggestions

### LP-01: No Build Tooling or Minification — OPEN

~6,860 lines shipped uncompressed. A simple esbuild step could bundle and minify to ~30-40% size, improving load times and enabling ES module imports.

---

### LP-02: CSS File Size at 2,089 Lines — OPEN

Single monolithic stylesheet. Consider splitting into component-specific files (`_cards.css`, `_studio.css`, `_modals.css`, `_responsive.css`) with CSS custom properties for theming.

---

### LP-03: Touch Event Handling for Mobile — OPEN

Several interactive elements use only click events. Touch-action CSS and pointer events would improve mobile interaction.

---

### LP-04: Potential Memory Leak in Toast System — OPEN

Rapid toast creation (multi-pull + milestone + achievement) can accumulate DOM elements before removal timers fire. Consider a max concurrent toast limit (e.g., 3) with immediate removal of the oldest.

---

### LP-05: No Automated Tests — OPEN

No test suite. Core calculation functions (income formulas, gacha rates, level costs, expedition rewards) are untested against regressions. Vitest + GitHub Actions CI would be a low-effort high-value addition.
